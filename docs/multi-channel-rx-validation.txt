One RX stream can select multiple distinct, non-conflicting handles, with
one card-level receive worker. All selected handles must share the same
actual sample rate. Setup and activation both check rates. The SDK conflict
query rejects invalid combinations before setup changes card configuration.
Immediate starts use the RX-only synchronized multi-start API. Digital RF
counters align a bounded set of per-handle pending blocks into shared planar
queue entries, so partial reads and queue eviction advance every plane together.
The system timestamp retains the first requested channel's original tick
and exact crop/sample offset; alignment never uses rounded nanoseconds.

Queue loss, hardware overrun, or a missing RF interval marks a shared gap.
A caller receives the retained contiguous prefix, then SOAPY_SDR_OVERFLOW,
then samples after the gap. Reversed buffer order is supported. All output
pointers are validated before consuming samples. CS16 and CF32 use the same
alignment path. An overlapping/backward RF counter fails the session because
samples from distinct counter epochs cannot safely be paired.

An SDK batch stop returning -ENODEV does not prove every selected handle
stopped. The adapter queries remaining selected streaming handles on each
multi-stop attempt and retains ownership on ambiguous or failed cleanup.
Regression cases exercise partial release and retry without stopping unrelated
handles. One RX stream token and one TX stream token per device remain the
ownership model; TX remains single-channel.

Limits and upstream submission
This is bounded digital receive-path validation. It does not establish analog
RF phase coherence, long-run performance, PPS behavior, multi-card physical
operation, or TX correctness. Only NV100 multi-channel behavior has hardware
acceptance here. Unsupported synchronized-start products fail explicitly.
The known NV100 explicit-topology-apply ENOTSUP observation remains recorded
in docs/nv100-validation.txt; the tested path uses legacy RX-only APIs.

This larger feature is preserved on the fork for review and later extraction.
It builds on the tested seven-PR integration checkpoint; it is not an eighth
upstream PR containing those unrelated changes. Keep upstream contributions
